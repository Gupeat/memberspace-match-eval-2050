# Rework v3 - response to the round-2 review

This repository is the complete, public, reproducible delivery for ClawHunt task #2050.
It responds to the round-2 review (delivery v3). The review accepted the delivery form
(public repo, dataset, stats, per-metric tests, exit codes, comparison report) and found
one blocking item: the labels were generated by the same formula as `weights/v2.json`, so
v2 scored itself.

The previous data also had fixture defects: capabilities were assigned by cycling an index,
so company names and capability cards did not match; only 13 of 16 capabilities ever
appeared; required capabilities were always three while a company could cover at most two,
so 3/3 coverage was impossible. Fixing only the label wording would not have survived a
data-level review, so this round rebuilds the fixture and the labeling method.

## What changed

1. **Hand-authored companies, deterministic fixture derivation** - `scripts/fixture_spec.py`
   defines all 40 companies explicitly, with capability cards that match company names and
   all 16 capabilities represented. The 30 supplies are derived from the companies
   (c001-c029 + c032; s009/s018/s028 paused); the 60 demand metadata rows are derived from
   eight demand types and 2-3 capability variants. Each demand requires two or three
   capabilities, so full coverage is possible; 113 of 190 positive labels fully cover the
   required set (52 at 3/3 and 61 at 2/2), and 77 cover 2/3.
2. **Six editorial slots with abstention** - `scripts/labeling.py` selects at most one
   company per slot: capability_lead (IDF rarity density), case_strength (curated verified
   cases), responsiveness (curated response days vs the demand tolerance), industry_fit,
   regional_fit and capacity_fit. Each slot is a lexicographic key with an explicit
   qualification predicate; there is no weighted sum and no 0.40/0.20/0.20/0.20 composite.
   If no qualified candidate remains, the slot abstains. Therefore each demand has 1-6
   positives, not a forced six.
3. **Label-only signals** - `data/editorial-signals.json` carries verified_cases,
   response_days and max_response_days. `match_eval` never reads this file. The capability
   slot uses corpus IDF density, not the evaluator's coverage ratio. The case count is
   company-level, not split by capability; this is disclosed rather than presented as
   domain-specific evidence. Industry, region and capacity slots are different editorial
   aggregations of facts the evaluator also uses; only case_strength and responsiveness are
   wholly new signals.
4. **Frozen labels, no bootstrap cycle** - `scripts/build_annotations.py` reads the fixture
   and the label-only signals, never weights or generated demands, and writes
   `data/annotations.json`; `scripts/generate_dataset.py` only applies it. The old cycle
   (builder -> generated demands -> builder) is gone.

## Evidence

- `tests/test_dataset.py` uses AST import checks: generator, builder, labeling and fixture
  must not import `match_eval` or `weights`.
- `tests/test_labeling.py` has golden SHA-256 values, replays every one of the 60 demands
  through the six slots, and rewrites v1/v2 weights to arbitrary values, reruns both scripts,
  and asserts all four data files are byte-identical.
- `tests/test_label_independence.py` replays the d052 dominance witness and exhausts all
  1771 grid weights to assert that no non-negative four-feature weight can place all six
  positives of d052 in top6.
- `scripts/manual_review.py` replays the six slots and the four negatives with the same
  `labeling` module and compares each `(slot, company_id)` and `(company_id, reason)`; it is
  not a self-check against fields the builder itself wrote. Default status is
  `pending-human-signoff`; only `--reviewer` plus `--attest` records `human-reviewed`.
- `scripts/label_sensitivity.py` replaces only the positives with random draws, using each
  demand's actual positive count. Under the production floor (coverage >= 2), random labels
  favour v2 500/500 with median +0.075438; the actual labels are at the 41.0th percentile
  (+0.075025), i.e. not tuned to favour v2. Under coverage >= 1, v2 wins 484/500; with no
  floor, only 247/500. This is why the delivery does not claim that +0.075025 proves v2 is
  better.
- `scripts/weight_grid.py` enumerates all 1771 non-negative four-feature weights at 0.05
  steps. The best weight in the grid covers only 58/60 demands (capability 0.65 / industry
  0.00 / region 0.15 / capacity 0.20; positive recall 188/190), with best NDCG@10=0.996243.
  This is not a grid-resolution issue; there are two structural failures, not one:
  in d052 the unlabelled but eligible c006 strictly dominates the labelled c022
  (capability 1.0 vs 2/3; industry, region and capacity equal), so any non-negative weight
  ranks c006 above c022; if c022 enters top6, c006 must too, and six positives plus c006
  need seven slots. d036 has five positives; c003/c006/c013/c021 have capability 1.0 and
  strictly beat c004/c024 at 2/3, while c022's region lead (or the company_id tie-break when
  capability and region weights are zero) leaves no six-slot arrangement containing all five.
  `artifacts/weight-grid.json` records both in `failed_demands` (best_covered, missing and
  extra candidates), and `tests/test_label_independence.py` asserts d036 and d052 over the
  full grid. The repository therefore claims "labels are not generated from v1/v2 weights,
  and their top6 set cannot be reproduced by any non-negative four-feature weight", but not
  orthogonality with the evaluator's business facts.

All data is synthetic; no real companies, contacts or PII are included.

## Honest limits

The labels are synthetic editorial fixtures generated by a documented rule; they are not
human annotations. The review pack is pending human sign-off. The capability floor
("at least two required capabilities") is a business rule, not a scoring weight; it
systematically raises v2 under random label sets with the same floor. The actual label set
is not tuned to v2, but that still does not make 0.965123 a generalization result.
`case_strength` uses company-level case counts, not capability-specific cases. The labels
share company capability, industry, region and capacity facts with the evaluator; no
non-negative four-feature weight can cover every demand's top6 (best 58/60; d052 and d036 are
the two structural failures),
but that is not the same as independence from those business facts. See
`data/ANNOTATION.md`, `docs/LABEL-BASELINE.md` and `docs/EVALUATION-LIMITS.md`.
